## 使用哪一份代码

0.6.0 包含版本绑定、回归归因、有效值比较及逐字段契约演进的库 API。
可用 `moon add Noverberrain/configscope@0.6.0` 在自己的项目中引用。
下文 CLI 案例需要克隆仓库后运行；安装库不会把命令安装为系统可执行文件。
0.5.0 不含本轮新增 API，请勿用旧包代替 0.6.0 验证。
`scripts/check_published_package.py` 会在仓库之外的新项目安装发布包，验证 README
中的新 API 调用。2026-10-27 已从 Mooncakes 下载 0.6.0，独立项目检查与运行通过，
验证了候选可被接纳、有效值未保持及规则收紧三个新增 API 结果。

[提交 2021bfa 的公开 CI](https://github.com/Noverberrain/ConfigScope/actions/runs/40534643963)
已于本次材料核对时确认成功。运行中可查看 release-policy cases 摘要，
以及 `configscope-release-policy-reports` 附件。报告按工作流设置保留 14 天，
过期后可在本地重新生成；不要把附件保留时间理解为永久存证。

## 基础校验可复用后，项目仍承担什么

必填、类型、枚举和范围检查是可替换的基础层。目前仓库自己实现这些检查，
没有声称已接入其他校验库。若换成现有库，仍需处理下面的关系：

- 一条版本绑定明确给出 consumer、version、contract、baseline 和 baseline_id。
  这些是调用者声明的支持范围及历史引用，不根据文件名猜测版本，也不证明文件来源。
- 同一绑定契约分别检查历史和候选，以“路径＋问题种类”识别新增、已有和修复。
  同路径从类型错误变成越界，记为旧问题修复和新问题引入，不能当成历史问题豁免。
- 两份快照都合法时，比较声明路径的有效值与来源。缺失不等于 null，
  显式值被同值默认值接管只改变来源；不同默认值可能改变读取结果。
- 将各版本的候选接纳和有效值比较交给明确的发布策略，保留不可比较状态，
  并让文本／JSON 报告和退出码使用同一套阻断计算。
- 单独分析受支持的逐字段契约变化。其结论与具体候选的检查是两类证据，
  不用固定 JSON 增删改分类替代它们，也不将逐字段分析拼成全局兼容性证明。

以下案例展示上述关系，而不是只展示规则语法。

## 案例一：候选都合法，但不同版本读取结果不同

历史快照 [historical.json](../cmd/main/testdata/release/historical.json) 为 `{"timeout":30}`，
候选 [empty.json](../cmd/main/testdata/release/empty.json) 为 `{}`。
[v1 规则](../cmd/main/testdata/release/v1.json) 默认 timeout=30，
[v2 规则](../cmd/main/testdata/release/v2.json) 默认 timeout=10，两者都允许候选。
清单把两个版本各自的规则与历史文件绑定在一起。

```sh
moon run cmd/main -- release-check cmd/main/testdata/release/defaults.release.json --format json
moon run cmd/main -- release-check cmd/main/testdata/release/preserve.release.json --format json
```

| 清单策略 | 候选校验 | v1 有效值 | v2 有效值 | 预期决策／退出码 |
|---|---|---|---|---|
| accept | 全部通过 | 30 → 30 | 30 → 10 | allowed／0 |
| preserve-effective | 全部通过 | 30 → 30 | 30 → 10 | blocked／1 |

严格报告应有 `candidate_accepted: true`、`passed: false`，v2 的阻断代码为
`effective_value_changed`，路径为 timeout。报告只包含来源和是否变化，不输出数值。
表中的数值来自公开样本，便于人工解释。退出码 1 在这里是预期结果，不是程序崩溃。

## 案例二：来源变化不等于有效值变化

```sh
moon run cmd/main -- release-check cmd/main/testdata/release/preserve-equal.release.json --format json
```

该清单只要求支持 v1。timeout 从显式值切到同值默认值，报告应记录
`before: explicit`、`after: default`、`value_changed: false`，严格策略允许，退出码 0。
这说明删除字段不再被一律当成相同程度的消费方影响。

## 案例三：规则收紧，与实际候选的版本接纳分别给出证据

```sh
moon run cmd/main -- contract-evolve cmd/main/testdata/evolution/old.json cmd/main/testdata/evolution/new.json --format json
moon run cmd/main -- release-check cmd/main/testdata/release/rejected.release.json --format json
```

第一条使用独立演进样本：mode 枚举缩小，timeout 上限从 60 改为 40，默认值不变。
应有两个 tightened 条目；这是诊断完成，退出码 0，`is_release_gate: false`。

第二条使用版本绑定样本：历史 timeout=30，候选显式 timeout=45。
v1 上限 60 接受，v2 上限 40 拒绝；v2 应新增 above_maximum，整体 blocked、退出码 1。
该样本的两个版本默认值不同，但候选含显式值，默认值不参与这次取值。
两个命令分别提供演进证据与候选决策；当前不会自动从 release 清单推断新旧契约关系。

## 案例四：历史非法不能伪装成“没有有效值变化”

```sh
moon run cmd/main -- release-check cmd/main/testdata/release/preserve-unknown.release.json --format json
```

这里 v2 绑定的历史 timeout=45 已超过其上限，候选缺失字段后使用合法默认值。
候选接纳为 true，上限问题已修复；有效值结果应为不可比较，
`effective_values_preserved: null`，严格策略因 effective_incomparable 阻断，退出码 1。
这表示无法确认保持不变，不是证明该候选业务上一定不兼容。

## 案例五：同一候选的新增问题与历史问题不同

```sh
moon test consumer_release_test.mbt --deny-warn
```

[首个回归测试](../consumer_release_test.mbt) 将 v1 历史 port=80、token 存在，
v2 历史 port=0、token 缺失，分别绑定后比较候选 port=80、token 缺失。
v1 的 token 缺失是新增问题；v2 的 token 缺失是已有问题，port 越界已修复。
两者仍拒绝候选，已有问题不会因为不是本次引入就自动放行。该用例通过断言验证归因。

## 不确定结果与能力限制

```sh
moon run cmd/main -- contract-evolve cmd/main/testdata/evolution/old.json cmd/main/testdata/evolution/unknown.json --format json
```

此例变动默认值，结果应为 unknown／default_changed。命令退出码 0 只表示分析完成，
不能当成允许发布。全局字段关系、任意条件表达式、业务副作用及应用运行结果不在证明范围。
条件规则只支持引用无条件规则的单次相等判断；有效值只按声明推导，不加载配置或执行消费方。
结构门禁保留为辅助检查，与新的版本绑定流程分开；历史合并 API 为兼容旧调用保留。

## 重新生成 CI 案例证据

Windows PowerShell：

```powershell
python scripts/check_release_cases.py "$env:TEMP/configscope-release-$(Get-Date -Format yyyyMMddHHmmss)"
```

脚本验证 5 个固定案例的精确退出码、JSON、绑定和阻断原因，输出每例报告与 results.json。
预期阻断算验证成功；文本错误、崩溃或错误归因不能算成功。它不是部署工具，也不是任意项目的验收保证。
